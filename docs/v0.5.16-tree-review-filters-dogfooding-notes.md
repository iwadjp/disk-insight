## 1. Problem

TreeView shows where disk space is used. The next question users ask:

- Which large areas are candidates for manual review?
- Which areas are dangerous to touch manually?
- How can I tell system / app-managed / user-data / temp / cache / dev-dependency apart?

**disk-insight does not recommend deletion.** All guidance is review-oriented:

- No "safe to delete"
- No "delete recommended"
- No "deletable"
- Only: review / caution / guidance

---

## 2. Rejected Approach: SelectedFolderCard Guidance

v0.5.16-C added cleanup guidance to the `SelectedFolderCard` right pane. Rolled back in v0.5.16-C2.

**Why rejected:**

- Became "select first, read explanation later" — not the goal
- Goal is finding candidates *in* the TreeView, not reading explanations after selection
- Does not help discoverability
- Cluttered the right pane

**What was kept:**

- `ui/src/cleanupSafety.ts` — pure TypeScript classifier
- `classifyCleanupSafety()` function — reused by view filters

---

## 3. Accepted Approach: View Selector

A view selector in the TreeView header was adopted.

Current views:

```
All
Large review
Reviewable areas
Caution areas
```

**Why accepted:**

- Does not pollute the normal TreeView
- Candidates are filtered only when needed
- Discovery happens inside the TreeView itself
- No always-on badges / markers / row backgrounds to create visual noise

---

## 4. View Definitions

### All

Normal TreeView.

- **Data source:** loaded TreeView rows
- No filter
- Occupancy bar / percent / size columns visible

### Large review

Find large review candidates from global scan results.

- **Data source:** `data.top_directories + data.top_files`
- **Display:** flat list inside the TreeView pane
- **Included categories:**
  - `temp-candidate`
  - `cache-candidate`
  - `dev-dependency`
  - `recycle-bin`
- **Excluded:**
  - `user-data`
  - `app-managed`
  - `protected-system`
  - `unknown`
- **Size threshold:** `>= 1 GiB`
- `user-data` is excluded — these are per-user personal files, not bulk cleanup targets
- Displayed as "Large Review Candidates" (not a raw top-files dump)
- Add/Remove bookmark available from context menu

### Reviewable Areas

Filter loaded TreeView rows for large non-caution areas.

- **Data source:** `visibleRows`
- **Display:** normal TreeView filter (same row layout as All)
- **Included:**
  - `user-data`
  - `temp-candidate`
  - `cache-candidate`
  - `dev-dependency`
  - `recycle-bin`
  - `unknown`
- **Excluded:**
  - `protected-system`
  - `app-managed`
- **Size threshold:** `>= 1 GiB`
- Named "Reviewable" not "Safe" — includes user-data and unknown, neither of which is inherently safe to remove

### Caution Areas

Filter loaded TreeView rows for system/app-managed areas.

- **Data source:** `visibleRows`
- **Display:** normal TreeView filter
- **Included:**
  - `protected-system`
  - `app-managed`
- **Excluded:** everything else
- **Size threshold:** none
- Purpose: know which large areas to avoid touching manually; use Windows or app settings instead

## 5. Data Source Decision

### Large review: top scan results, not visibleRows

**Why:**

- `visibleRows` reflects only expanded/loaded UI state
- `temp`, `cache`, `node_modules`, `$Recycle.Bin` typically live deep in unexpanded subtrees
- Using `visibleRows` produced empty results in practice (confirmed in v0.5.16-F)
- The purpose of Large review is "find large candidates across the full scan", not "filter current tree context"

### Reviewable areas / Caution areas: visibleRows is correct

**Why:**

- These are TreeView-context filters — the user is filtering what they can see in the current tree
- Role is different from Large review
- `loaded rows` origin is explicitly shown in header and footer

## 6. UI Decisions

### Adopted

| Decision | Reason |
|----------|--------|
| View selector in header | Non-intrusive; only active when switched |
| Non-All view header block | Context visible without reading footer |
| Footer count-only (after v0.5.16-K) | Conditions are in header; footer focuses on counts |
| Large review flat list | tree hierarchy irrelevant for global top results |
| Category label in Large review rows | Shows why each item was surfaced |
| Bookmark from Large review context menu | Lets user flag items without leaving the view |
| `>= 1 GiB` fixed threshold | Simple; matches Large review threshold; avoids threshold UI complexity |

### Rejected

| Decision | Reason |
|----------|--------|
| Row background highlight | Visually noisy; highlights arbitrary rows in normal tree |
| Always-on badges on TreeView rows | Clutters every row even when not in review mode |
| Safety color mixed into occupancy bar | Conflates "size" and "safety" in one visual encoding — highest misleading risk |
| SelectedFolderCard guidance | "Select then read" flow; not discovery |
| "safe/deletable" wording | Implies deletion recommendation |
| user-data in Large review | User personal files are not bulk cleanup targets |
| Percent threshold | Added complexity; no clear user need established |
| Threshold UI | Premature; 1 GiB fixed is sufficient for now |
| Automatic recursive expansion/jump from Large review row | Deferred; complex Tauri state interaction |

## 7. Current Known Limitations

- Large review is derived from top N folders/files; candidates outside that count range are not shown
- Large review is a flat list — not the actual TreeView hierarchy
- Reviewable areas / Caution areas cover only loaded (expanded) rows; unexpanded subtrees are excluded
- Large review has no keyboard navigation (deferred)
- Record index jump / recursive expand from Large review rows is not implemented
- Classifier is path-based heuristic only — not authoritative safety judgment
- `ProgramData\*\Cache` is treated as `app-managed` (safe-side decision), even though it might be safe to clear via the relevant app
- Cleanup of `user-data` would require a different, separate design
- `target` segment is classified as `dev-dependency` which can produce false positives for non-Rust/build-output folders

## 8. Dogfooding Checkpoints

Items to verify during actual use:

- [ ] Does Large review surface genuinely useful candidates? (`.gradle`, `node_modules`, `Temp`, `$Recycle.Bin`)
- [ ] Are `.gradle`, `npm`, `node_modules`, `Temp`, `$Recycle.Bin` classified in a way that feels right?
- [ ] Does Reviewable areas serve as a useful complement to Caution areas?
- [ ] Are the 4 views (All / Large review / Reviewable areas / Caution areas) the right number, or too many?
- [ ] Does the header block take too much vertical space when switching views?
- [ ] Is the bookmark flow natural when used from Large review?
- [ ] Could any wording be misread as "safe to delete" by a new user?
- [ ] Does the UI work well in Company-safe mode (external demo scenario)?
