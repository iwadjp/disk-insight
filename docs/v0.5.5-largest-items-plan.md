# v0.5.5-largest-items-plan

# 1. 目的

* disk-insight の「選択フォルダ配下で何が大きいか」を見つけやすくする
* global Top N filter ではなく、selected folder subtree 全体を対象にした true largest folders / files を目指す
* WizTree の「大きい対象を見つけやすい」体験に近づける
* v0.5.5 では、まず設計 → Rust command → UI 接続の順で安全に進める

# 2. 現状仕様

* `data.top_directories` / `data.top_files` が Rust 側で global Top N として生成されている。
* `top_n` は Top selector の値に基づく（既定 10, 30, 100 など）。
* Frontend 側では `filterByDir` により `selectedDir.path` を前方一致検索して表示している。
* これは selected folder subtree 全体の再ランキングではない。
* v0.5.4 の “Top scan results” という見出しは現状仕様としては正しい（「スキャン結果の中の Top」であって「このフォルダ内の Top」ではない）。

Current TopDirs / TopFiles are filtered from the global Top N scan results, not computed from the selected folder subtree.

# 3. 問題点

* **不完全な表示**: C:\Ap 配下で最大のフォルダ / ファイルでも、global Top N（例えばドライブ全体で Top 100）に入っていなければ、C:\Ap を選択しても何も表示されない。
* **中規模フォルダでの不便**: 数 GB 程度のフォルダでは “No top files under this folder” になりやすく、調査が捗らない。
* **ユーザーの期待との乖離**: ユーザーが「このフォルダを選択した」ときは、そのフォルダ内で何が容量を占めているかを知りたい。
* **既存機能の限界**:
    * `DirectChildren`: 直下しか分からない。3 階層下の巨大ファイルが見えない。
    * `Search inside`: 名前検索であり、「名前は知らないが大きいものを探したい」用途には使えない。

# 4. 実装方式比較

## 案A: Frontend only subtree ranking
結論: 却下。
理由:
* フロントには subtree 全体の全ノードがない。
* `childrenByParent` は lazy loading されているため、未展開の階層の情報が欠落する。
* 全ノード取得には大量の `get_children` IPC が必要になり、パフォーマンスが著しく悪化する。

## 案B: Rust command get_largest_items_under
結論: **本命。**
理由:
* Rust 側の `ArenaCache` には全ノード情報（数百万ノード）がメモリ上にある。
* `dir_children` (FRN -> children indices) を使って subtree を高速に走査できる。
* `search_subtree` と同様の BFS/DFS パターンを流用でき、実装が容易。
* path 再構築（重い処理）は最終的にランキングに入った上位 N 件に対してのみ行えばよい。
* UI からは `record_index` (FRN) 指定で呼べる。

## 案C: scan 時に各 directory ごとの top descendants index を作る
結論: v0.5.5 では過剰。
理由:
* 全ディレクトリに対して top N を保持すると、scan 時間とメモリ消費が劇的に増加する。
* ユーザーが一度も選択しないフォルダのインデックスも作ることになり、効率が悪い。
* 案B (オンデマンド計算) が十分速い（数百 ms 以内）なら、事前インデックスは不要。

## 案D: DirectChildren 強化のみ
結論: 不十分。
理由:
* サブディレクトリの深い階層にある大物を見逃す。
* WizTree のような「フォルダツリーを降りながら大物を追いかける」体験を実現できない。

# 5. 推奨アーキテクチャ

案Bを採用する。

### Rust 側
* `get_largest_items_under(record_index, limit)` Tauri command を追加。
* `ArenaCache::largest_items_under(parent_frn, limit)` メソッドを実装。
    * `search_subtree` と同じ BFS/DFS パターンを利用。
    * `BinaryHeap` (Bounded Min-Heap) を使用して、folders (subtree_size 降順) と files (final_alloc 降順) を別々に Top N 保持。
    * 走査終了後、上位 N 件に対してのみ `reconstruct_path` を実行。
* `record_index` (FRN) を主キーにする。

**返却型案:**
```rust
#[derive(serde::Serialize)]
pub struct LargestItemsResult {
    pub folders: Vec<JsonDirEntry>,
    pub files: Vec<JsonFileEntry>,
    pub truncated: bool, // 走査制限などに達した場合（将来用）
}
```

### Frontend 側
* `selectedDir.record_index` が変更された際に、新しい `get_largest_items_under` コマンドを発行。
* 150〜250ms 程度の debounce を入れ、頻繁なフォルダ切り替え時の負荷を軽減。
* Per-folder cache を検討（同一セッション内）。
    * ただし、scan / drive 切替 / sample load 時には clear すること。
* 取得した `LargestItemsResult` を、既存の `DirectoriesTable` / `FilesTable` に渡せるように UI コンポーネントを整理する。

# 7. Performance

* Rust 側は全て in-memory の `ArenaCache` 走査なので、ディスク IO は発生しない。
* 数百万ノードの走査でも、単一の subtree であれば現代的な CPU では 100ms 未満で終わる可能性が高い。
* ただし、ドライブ全体の root を指定した場合は数百万ノードの全走査になるため、実測が必要。重い場合は root のみ既存 global top fallback を使う。
* `limit` は既定 50、上限 200 程度とする。Top selector の値とは独立させて、常に十分な数（例: 50）を出す方が利便性が高い。

# 10. 実装前に決めるべきこと

1. **Largest folders の表示方針**
    * WizTree 同様、subtree 内の全フォルダをフラットにランキングする。
    * 親フォルダと子フォルダが共にランクインする場合、両方を表示する。
2. **Top selector との連動**
    * 既存の 10 / 30 / 100 / 500 selector と連動させるか？
    * 独立させて固定（例: 50）にするか？（フォルダ配下の調査には 50 もあれば十分なことが多いため）
3. **Root 選択時の挙動**
    * 全走査のコストが許容内なら `get_largest_items_under(root)` に統一。
    * 許容外なら、Scan 時に作った global top-N を fallback として使う。
4. **Empty state の文言**
    * 何もファイルがない空フォルダの場合の表示。
