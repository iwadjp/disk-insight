# v0.5.17 Multi-select Move — Design Notes

## Status

- **Design only.** v0.5.17-B does not implement anything.
- No app code, UI, classifier, or filter condition changes.
- This document compares workflows and proposes a phased path before any
  multi-select / move feature is built.

---

## 1. Problem Statement

After finding large items in TreeView / Large review / Reviewable areas, users
sometimes want to relocate or stage several items together, not one at a time.

Example scenarios:

- Move several old project folders to `D:`
- Stage several VMs / build artifacts / cache-like folders for relocation
- Take multiple Large review candidates beyond a single bookmark and organize them

The risk: **a wrong batch move is close to a batch delete in consequence.**
Moving the wrong set — especially across drives — can break apps, lose data, or
strand system/app-managed areas.

---

## 2. Non-goals (v0.5.17-B)

This phase does **not** cover:

- Implementation of any kind
- UI changes
- Delete
- Cut / Paste
- Permanent delete
- Full Windows shell context-menu integration
- Explorer `IContextMenu` embedding
- Enabling move in Company-safe mode
- Automatic deletion recommendation
- Any wording that asserts "safe to delete" / "safe to move"

---

## 3. Existing Safety Model (context)

The design must fit the conventions already shipped:

| Mechanism | Behavior |
|-----------|----------|
| **Advanced Mode** | Session-only (non-persistent). Off by default every launch. Required for "Move to Recycle Bin". Enabling shows a warning modal acknowledgement. |
| **Company-safe mode** | Seals terminal / recycle / admin launch. Destructive or state-changing file operations are suppressed. |
| **Recycle confirm modal** | Per-item confirmation, shows path + size, lists path-based `warnings`, and requires an "I understand this target may be high risk" checkbox for risky targets. |
| **`classifyCleanupSafety()`** | Path-based heuristic only. Used for review/caution framing, never as an authoritative safety verdict. |

Any multi-select move must be **at least as conservative** as the single-item
Move to Recycle Bin flow — preferably more, because it touches many items at once.

---

## 4. Candidate Workflows

### Option A: Explorer handoff

Select multiple items in disk-insight, then open their locations in Explorer or
copy their paths. The actual move happens in Explorer.

- **Pro:** Safe; light to implement; reuses the OS file manager users trust.
- **Con:** Not self-contained in disk-insight.

### Option B: Multi-select + "Move to folder..." inside disk-insight

Select multiple items, pick a destination folder, and move them within the app.

- **Pro:** Convenient; self-contained.
- **Con:** Dangerous; heavy. Needs confirmation, rollback design, partial-failure
  handling, conflict resolution, post-move rescan.

### Option C: Multi-select bookmarks / staging list only

Add multiple items to a "staging list" (review list). No file operation yet.

- **Pro:** Safe; lets the user collect and review before acting; natural
  precursor to any real move.
- **Con:** Does not move anything by itself (by design).

### Option D: "Open containing folders / copy paths" batch actions

Batch-copy selected paths, or open their parent folders.

- **Pro:** Assists organization without moving; low misoperation risk; likely
  acceptable even in Company-safe mode.
- **Con:** Not a move.

---

## 5. Recommended Direction

Working hypothesis (most conservative first):

1. **C — staging / review list enhancement** (no file op)
2. **D — batch copy paths / Explorer handoff**
3. **B — real "Move to folder..."** only if still needed after dogfooding

Rationale:

- Jumping straight to move is dangerous.
- A staging/review list composes well with existing bookmarks.
- The natural flow is: find candidates in Large review → stage/bookmark →
  verify manually → act in Explorer (or, eventually, in-app move).
- Matches disk-insight's safe-viewer / cautious-operations posture.

---

## 6. Selection Model

Views where multi-select could apply:

- TreeView (All)
- Large review flat list
- Reviewable areas
- Caution areas
- Bookmarks panel
- Insights lists

Interaction options considered:

| Mechanism | Note |
|-----------|------|
| Ctrl-click | Implicit; higher misoperation risk |
| Shift-click range | Implicit; range mistakes are easy |
| Checkbox | Explicit; visible selection state; safer |
| Keyboard selection | Needs clear focus + selection separation |
| "Add to review list" action | Explicit, per-item; safest entry point |
| Selected count display | Required for any batch action |
| Selected paths preview | Required before any destructive/move step |

**Recommendation for the first stage: explicit checkbox or "Add to review list"**,
not implicit Ctrl/Shift selection. Implicit multi-select makes accidental
large selections too easy, which is exactly the risk we are guarding against.

## 7. Safety Classification Integration

How `classifyCleanupSafety()` informs a future move flow:

| Category | Move-flow treatment |
|----------|---------------------|
| `protected-system` | Exclude from move, or block with strong warning |
| `app-managed` | Warn by default; prefer app settings / uninstaller |
| `user-data` | Neutral — but **not** a move/delete recommendation |
| `temp-candidate` / `cache-candidate` / `dev-dependency` / `recycle-bin` | Review candidate; **not** asserted as "move safe" |
| `unknown` | Treat cautiously (lean toward caution, not toward action) |

Constraints:

- Classification is a path-based heuristic; it does **not** guarantee that an
  item can or should be moved.
- UI must never say "safe to move".
- If any selected item is `protected-system` / `app-managed`, the batch action
  should warn or block, mirroring the single-item recycle warning model.

---

## 8. Company-safe Mode

In Company-safe mode:

- **Real move: disabled.**
- Do not add new destructive / state-changing file operations.
- Allowed: bookmark / staging / copy path / show in Explorer.
- Batch copy paths: acceptable candidate.
- Explorer handoff: evaluate against the existing Company-safe sealing of
  terminal/recycle/admin launch — keep consistent.

---

## 9. Advanced Mode

If a real in-app move is implemented, gate it behind Advanced Mode:

- "Move to folder..." available **only** when Advanced Mode is ON.
- Confirmation modal required.
- Modal shows: selected item count, total size, destination path.
- If selection contains `protected-system` / `app-managed`: block or strong warning.
- Advanced Mode stays session-only (non-persistent), consistent with the recycle flow.
- With Company-safe ON, Advanced Mode is suppressed → move is unreachable.

---

## 10. Failure Handling (for a real move)

Designs needed before implementing Option B:

- Move destination validation (exists, writable, not inside source)
- Same-drive vs cross-drive (rename vs copy+delete; very different cost/risk)
- File-exists conflict resolution (skip / rename / overwrite)
- Partial success (some moved, some failed) — clear reporting
- Permission denied
- In-use / locked files
- Rollback may be impossible once some items have moved
- Post-move stale view (paths no longer valid)
- Rescan prompt after move
- Undo may not be feasible — do not promise it lightly
- Difference between Windows shell move semantics and
  `std::fs::rename` / copy + remove (links, ADS, attributes, permissions)

---

## 11. UI Wording

**Forbidden:**

- Safe to move
- Safe to delete
- Delete recommended
- Can move safely
- Cleanup safe

**Candidate wording:**

- Review list
- Staging list
- Prepare for manual review
- Move requires confirmation
- This action changes files on disk
- Use Explorer if unsure

---

## 12. Phased Implementation Proposal

| Phase | Scope |
|-------|-------|
| **v0.5.17-B** | Docs only (this design). |
| **v0.5.17-C** | Introduce "review list" / staging-list concept. No file operation. |
| **v0.5.17-D** | Allow adding to the review list from Large review / Reviewable / TreeView / Bookmarks. |
| **v0.5.17-E** | Batch copy paths / open in Explorer for the review list. |
| **v0.5.18+** | Evaluate real "Move to folder..." in Advanced Mode only. |

Each phase is independently shippable and reversible; later phases are only
pursued if dogfooding shows the earlier, safer phases are insufficient.

---

## 13. Open Questions

Kept deliberately unresolved:

- Should disk-insight move files at all, or is Explorer handoff enough?
- Multi-select via checkbox or Ctrl/Shift?
- Should the review list be integrated with bookmarks, or kept separate?
- How is the move destination chosen (folder picker, bookmarked target, recent)?
- How is the stale scan view handled after a move?
- Can undo realistically be offered?
- Should any of this ship before release, or stay dogfooding-only?
