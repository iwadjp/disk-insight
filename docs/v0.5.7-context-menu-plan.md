## 0. 結論（先に出す）

| 方式 | 判定 | 一言 |
|------|------|------|
| **案A: 本物の Shell context menu（IContextMenu）を disk-insight 内に表示** | **却下** | disk-insight の安全モデルを設計上破壊する。永久削除・第三者コード実行を素通しする。 |
| **案B: Explorer に handoff** | **採用（常設の逃げ道）** | 危険操作は Explorer に委譲。安全境界が明確で誠実。既に 8 割実装済み。 |
| **案C: disk-insight 自前メニューを curated 拡張** | **採用（主軸）** | 各 verb を Rust 側で個別検証。既存アーキテクチャと完全に一致。漸進的に出荷可能。 |

**推奨アーキテクチャ: 「C を主軸、B を常設の逃げ道」の二層構成。A は当面の非ゴールとして安全上の理由を明記して却下する。**

> disk-insight の安全保証は「**すべての破壊的操作が Rust の `validate_recycle_target` を必ず通り、
> 結果として Recycle Bin 移動しか起こさない**」という一点に集約されている。
> - 案A はこのモデルを**設計上破壊する**（素通し）。
> - 案B はこのモデルを**委譲で尊重する**（Explorer の責任に移す）。
> - 案C はこのモデルを**curation で拡張する**（verb ごとに同じ検証を通す）。
>
> 製品の差別化要因は「**安全な**ディスク掃除」である。よって curated surface を広げ、残りは委譲する。

## 1. 前提（既存実装の調査結果 / 確認済み事実）

設計に直結する、現行コードベースの確認済み事実：

- **右クリックメニューは `SafeContextMenu`（`ui/src/main.tsx:807`）に集約済み。**
  TreeView / DirectChildrenPanel / DirectoriesTable / FilesTable / SubtreeSearchPanel が
  すべてこの共有コンポーネントを使う。→ 項目を 1 箇所変えれば全サーフェスに反映。
- **現在の自前メニュー項目（v0.5.7-B 実装後の実物）:**
  - Show in Explorer（`open_in_explorer` / `select_in_explorer`、v0.5.7-A で統合）
  - Open terminal here（`open_terminal_at`、v0.5.7-B で追加、Safe/Advanced 両方）
  - Show properties（`show_properties`）
  - Copy path / Copy as path（フロント `navigator.clipboard`）
  - Move to Recycle Bin（**Advanced Mode ON 時のみ**、`move_to_recycle_bin`）
- **⚠ v0.5.7-A/B は「Explorer相当メニュー問題の解決」ではなく「安全な curated menu の改善」である。**
  詳細は §0.5 参照。
- **`show_properties` は既に `SEE_MASK_INVOKEIDLIST` 経由で内部的に IContextMenu を使っている**
  （`src-tauri/src/main.rs:792`）。これは「**特定の単一 verb を安全に借りる**」正しい先例。
  将来もし shell verb を 1 つ増やすなら、メニュー全体を `QueryContextMenu` で晒すのではなく、
  この**特定 verb invoke** の作法を踏襲する。
- **破壊的操作は `move_to_recycle_bin`（`IFileOperation` + `FOF_ALLOWUNDO | FOFX_RECYCLEONDELETE
  | FOFX_EARLYFAILURE`）の 1 本のみ。** その手前で必ず `validate_recycle_target` /
  `block_reason_for_recycle_target`（`src-tauri/src/main.rs:587-706`）が走る。
  - drive root / depth < 2 をブロック
  - `FILE_ATTRIBUTE_SYSTEM` をブロック
  - SystemRoot / windir / ProgramFiles(x86) / ProgramData / `$Recycle.Bin` /
    `System Volume Information` をブロック
  - USERPROFILE root / Users 直下 1 階層をブロック
  - hidden / read-only は警告
- **完全削除（DeleteFile / RemoveDirectory）は実装が存在しない**（意図的）。
- **Recycled visual state**: 移動後も行を消さず、`record_index` または `path` 一致で
  取り消し線 + badge 表示（`isItemRecycled`）。
- **Cargo features**: `Win32_UI_Shell` / `Win32_System_Com` /
  `Win32_UI_WindowsAndMessaging` / `Win32_Storage_FileSystem` が有効。
  ターミナル起動はプロセス spawn で足り、追加 feature 不要。

## 2. 目的

- WizTree の「TreeView から右クリックで思った操作ができる」常用感に近づける。
- DirectChildren / Largest items / TreeView いずれの行からも一貫したメニューを出す
  （既存の `SafeContextMenu` 集約を維持）。
- **Safe Mode を既定として維持**し、**Advanced Mode ON 時だけ**破壊的寄りの項目を出す。
- **disk-insight の安全モデル（全破壊操作が Rust 検証を通り Recycle のみ）を 1 ミリも崩さない。**

## 3. 各方式の詳細評価

### 案A: 本物の Shell context menu を disk-insight 内に表示

実装イメージ: `SHParseDisplayName` で PIDL 取得 → 親フォルダの `IShellFolder` →
`GetUIObjectOf(IID_IContextMenu)` → `QueryContextMenu` で HMENU 構築 →
`TrackPopupMenuEx` 表示 → `InvokeCommand` で選択 verb 実行。
オーナードロー submenu のため `IContextMenu2/3` のメッセージ転送
（`WM_INITMENUPOPUP` / `WM_DRAWITEM` / `WM_MEASUREITEM`）を window proc で処理する必要。

**致命的な安全上の問題（却下理由の核心）:**

1. **シェルの全 verb を晒す = disk-insight の安全ガードを完全素通し。**
   `InvokeCommand` を呼んだ瞬間、`validate_recycle_target` の depth/protected/recycle-only
   保証はすべて無効化される。
2. **永久削除が起こり得る。** シェルの "Delete" verb は既定では Recycle Bin に入るが、
   - Shift+Delete / レジストリ `NoRecycleFiles` / ドライブ別「ごみ箱に入れない」設定で**永久削除**
   - ごみ箱容量を超える大物は**永久削除**
   - リムーバブル/一部構成ではそもそもごみ箱なし
   → 「DeleteFile / RemoveDirectory による完全削除は禁止」の制約と**正面衝突**する。
   disk-insight が `FOF_ALLOWUNDO` で起こしていない永久削除を、止める手段がない。
3. **第三者シェル拡張の任意コード実行を出荷することになる。** 7-Zip / Git / TortoiseSVN /
   アンチウイルス / クラウド同期 / 「Send to」等が `QueryContextMenu` に項目を注入する。
   これらはすべて disk-insight の制御外のコードで、内容も挙動も保証できない。
4. **Cut/Paste/Move/Rename で system file を移動・改名され得る。** stale view も追跡不能。
5. **技術的にも高リスク。** Tauri/WebView2 上で古典的 HWND メッセージループを自然には持たず、
   `IContextMenu2/3` 転送のために hidden message window のサブクラス化が要る。
   STA スレッド固定・メッセージポンプ必須で、誤ればハング/クラッシュ。
   「unsafe は最小限に」の方針に最も反する重 unsafe コード。

**「verb をホワイトリストで絞れば？」も却下:** command ID は動的オフセットで、
`GetCommandString` による verb 同定はロケール/拡張で不安定。第三者のオーナードロー項目は
安全に introspect できない。結果「全複雑性 + 脆いフィルタ + それでも保証なし」で最悪。
→ shell verb を 1 つだけ足したいなら `show_properties` 流の**特定 verb invoke** が正解。

> **判定: 却下。** 技術的には最も "Explorer らしい" が、プロジェクトの安全制約と原理的に両立しない。
> 公開前のセキュリティ/安定性負債として最大。当面の**明示的な非ゴール**とする。

### 案B: Explorer に handoff

Explorer をその場所で開く / 項目を選択し、ネイティブの全メニューは**Explorer 側で**使わせる。
disk-insight はナビゲーション verb を提供し、危険サーフェスは Explorer の責任・Explorer の UX・
ユーザーが「アプリを出た」という明確な認識のもとに置く。

- **既に 8 割実装済み**（`open_in_explorer` / `select_in_explorer`）。
- 新規 unsafe ゼロ、COM プラミングゼロ。
- 安全境界が明確で誠実: 破壊的/任意操作は Explorer の責任。
- disk-insight 内に追跡不能な mutation が起きない（ユーザーは既に出ている）。
- 公開出荷が自明に安全。
- 短所: in-app ではない。1 クリックの context switch。

> **判定: 採用。常設の逃げ道。** Safe/Advanced いずれでも出す。
> 「フルパワーが欲しい」への誠実な答え = それを所有するツール（Explorer）へ誘導する。

### 案C: disk-insight 自前メニューを curated 拡張

React メニューを維持し、**個別に審査した first-class verb** を足す。各項目は
`validate_recycle_target` と同じ流儀で Rust command が検証する。すべて disk-insight が
明示的に選び、挙動を説明できる verb のみ。

- 既存アーキテクチャ（React メニュー + verb ごとの検証付き Rust command）と完全一致。
- 各 verb は監査可能。安全ガードが一元的・均一。
- Advanced 境界が意味を持ち続ける: OFF = 閲覧/ナビ/クリップボードのみ、
  ON = Recycle 追加（ガードを素通る項目は**一切足さない**）。
- 漸進的に出荷可能。各 verb が小さくレビュー可能な PR。
- 短所: 第三者拡張のない範囲なので literal Explorer parity には届かない
  （= 安全第一ツールにとってはむしろ feature）。

> **判定: 採用。リッチ化の主軸。**

## 4. Advanced Mode ON/OFF のメニュー設計

**ブライトライン: Advanced Mode ON でも、Rust 検証を素通る項目は一切出さない。生の shell verb invoke はしない。**

### OFF（既定 / Safe Mode）— 閲覧・ナビ・クリップボード・検査

| 項目 | backend | 区分 |
|------|---------|------|
| Open folder / Open containing folder | `open_in_explorer`（既存） | ナビ |
| Select in Explorer（file） | `select_in_explorer`（既存） | ナビ |
| **Show in Explorer**（フォルダ=open / ファイル=select の明示ラベル） | 既存再利用 | **handoff（案B）** |
| **Open terminal here（PowerShell）** | `open_terminal_at`（**新規**） | ナビ（非破壊） |
| Copy path / Copy as path | フロント（既存） | クリップボード |
| Show properties | `show_properties`（既存） | 検査 |

> **「Open terminal here」を OFF に置く根拠:** ターミナルを開くこと自体は破壊的でない
> （ユーザーが自分で当該フォルダに `cd` するのと等価）。WizTree/PowerToys 的な常用導線。
> ただし「シェルを与える」点を保守的に見るなら ON に寄せる選択もある。
> → **§5 のポリシー判断としてユーザーに最終確認する**（既定推奨は OFF）。

### ON（Advanced Mode）— curated な mutation を追加（依然ガード付き）

| 項目 | backend | 区分 |
|------|---------|------|
| （セパレータ + "Advanced" ラベルで視覚的に区切る） | — | — |
| Move to Recycle Bin | `move_to_recycle_bin`（既存、`validate_recycle_target` 経由） | 破壊（取り消し可） |
| Already moved to Recycle Bin（disabled） | — | 状態表示（既存） |
| （将来）Copy（CF_HDROP）= Explorer で paste 用 | 新規・任意 | §11 |
| （将来）Rename | 新規・先送り | §11 |

## 5. ユーザーに確認したいポリシー判断

1. **「Open terminal here」を Safe Mode (OFF) でも出すか、Advanced 限定にするか。**
   - 既定推奨: OFF でも表示（非破壊・高利便）。
2. **ターミナルの優先起動先**: Windows Terminal（`wt.exe -d <dir>`）優先 → 無ければ
   `powershell.exe`（作業ディレクトリ指定）にフォールバック、で良いか。
3. **MVP に「Show in Explorer」handoff の明示項目を足すこと**自体の可否（既存 open/select の再ラベル + 整理）。

## 6. Stale view（古い表示）の扱い

- **disk-insight 自身が行う操作（Recycle）**: 既存の recycled-badge モデルを維持
  （`record_index`/`path` 一致でマーク）。
- **Explorer 側で行われた操作（handoff 後）**: disk-insight は**原理的に追跡不能**。
  per-row のマジックはやらない。代わりに**正直で安価な**緩和:
  - ウィンドウが再フォーカスされた（= Explorer から戻った可能性）ときに、控えめな
    「Explorer でファイルを変更した場合、表示が古い可能性があります。Rescan を推奨」
    ヒントを出す。per-row ではなく全体バナー。
  - これは MVP 必須ではなく v0.5.7-C に回す。

## 11. 将来 GitHub 公開前に確認すべきリスク

- **管理者権限 × ターミナル起動**: 管理者で起動した disk-insight から開くターミナルが
  昇格を継承する挙動を README/runbook に明記（意図せぬ昇格シェルを避ける）。
- **コマンド注入**: `open_terminal_at` はパスを引数として渡すのみ（シェル文字列を組み立てない）。
  `std::process::Command` の引数渡し（シェル経由でない）を厳守し、パスに含まれる特殊文字で
  コマンド注入が起きないこと。
- **案A を将来も足さない方針の明文化**: 公開 README で「シェル拡張メニューは非対応（安全方針）」
  と謳い、ユーザー期待を正しく設定する。
- **CF_HDROP コピー（§9 将来候補）を入れる場合**: クリップボード経由でも disk-insight は
  paste 先を制御できない点を理解した上で、Advanced 限定・警告付きにするか再検討。
- **stale view の正直さ**: 「disk-insight は外部変更を自動追跡しない」ことを UI とドキュメントで
  明示し、Rescan 導線を常に近くに置く。
- **第三者コード非実行の保証**: disk-insight が起動するのは Explorer / Windows Terminal /
  PowerShell という OS 標準プロセスのみであること（任意の関連付けプログラムを起動しない）を
  セキュリティ説明として維持。
