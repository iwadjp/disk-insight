# v0.4.0 Plan — WizTree alternative candidate

**Date (initial)**: 2026-05-27  
**Date (Rev.2)**: 2026-05-27  
**Date (Rev.3)**: 2026-05-27  
**Status**: Planning only — no code changes in this document  
**Goal**: Define the conditions under which a user would choose disk-insight over WizTree  

> **Notation**  
> - `[measured]` — confirmed by actual measurement with specified conditions  
> - `[estimate]` — derived or calculated from measured data, not directly measured  
> - `[inference]` — reasonable extrapolation, not yet measured or calculated  
> - `[TBD]` — requires investigation or measurement before a decision can be made  

disk-insight v0.3.0 is a **safe-viewer** milestone: delete-free, reclaimable estimate, direct children navigation.
v0.4.0 targets **WizTree alternative candidate** — not a replacement, but a state where a user who knows WizTree
can consciously choose disk-insight for daily inspection work. The v0.3.0 safe-viewer positioning is preserved
and extended, not replaced.

---

## 1. Conditions for WizTree switchover

The following are the user-facing conditions that must hold for v0.4.0 to reach "alternative candidate" level.
Each condition maps to one or more implementation items in later sections.

### Condition 1 — Speed: disk-insight is not noticeably slower, or is faster

**Why**: WizTree's core selling point is speed. If disk-insight is meaningfully slower, there is no reason to switch.

**Honest current status:**

| Scenario | disk-insight | WizTree | Assessment |
|----------|-------------|---------|------------|
| C: warm (CLI release) | ~10s [measured] | ~15s [measured] | disk-insight likely wins — **but warm Tauri UI is estimated, not confirmed** |
| C: warm (Tauri UI) | ~10.5s [estimate] | ~15s | Estimate only — K-5d not executed |
| C: cold (Tauri UI) | ~23s [measured, cold-probable] | ~15s | ~8s slower. Cold condition confirmed probable. |
| C: cold (CLI) | unknown [TBD] | ~15s | K-1d was planned but never run |
| D: warm (CLI release) | ~59–63s [measured] | ~51s | **disk-insight is ~8–12s slower** |
| D: warm (Tauri UI) | unknown [TBD] | ~51s | Not measured |
| D: cold (Tauri UI) | ~81s [early estimate, pre-N-2b] | ~51s | Unreliable — conditions and build unknown |
| D: cold (CLI) | unknown [TBD] | ~51s | Not measured |

**Key correction from Rev.2:**  
Rev.2 described C: warm as evidence that "disk-insight is faster than WizTree overall." This is inaccurate.
- C: warm: disk-insight CLI ~10s vs WizTree ~15s — disk-insight is likely faster on C:, but warm Tauri UI is unconfirmed
- D: warm: disk-insight CLI ~59–63s vs WizTree ~51s — **disk-insight is slower on D:**
- "disk-insight overall faster than WizTree" is NOT established — C: is favorable, D: is not

**Also note**: README says D: ~54s, but K-5b (release, post-N-2b) measured ~59–63s CLI warm.
The discrepancy is likely due to N-2b (`wof_size_map` addition) or measurement condition differences.
The README figure is probably outdated. [TBD: reconcile with a fresh measurement]

**Speed goal for v0.4.0:**
- C: warm Tauri UI: confirm ≤12s (K-5d measurement required first)
- C: cold Tauri UI: Target A ≤18s / Stretch ≤15s (see Section 4)
- D: warm Tauri UI: measure first; then set target (goal: ≤55s to close gap with WizTree ~51s)
- D: cold Tauri UI: measure first; no target set until data exists

### Condition 2 — TreeView UI: easy to identify deletion candidates

**Why**: WizTree's tree shows Name / Size / Type with proportional size bars, making large items visually obvious. disk-insight currently shows numeric sizes without visual weight.

Key gaps:
- No proportional size bar in tree rows [measured — not implemented]
- No file type / category column [measured — not implemented]
- Folder vs file distinction is subtle [measured — not implemented]
- All rows look similar regardless of size [measured — not implemented]

See Section 5 (Explorer-like TreeView UI).

### Condition 3 — Right-click context menu: equivalent to Explorer

**Why**: WizTree exposes the Windows Explorer shell context menu on right-click. disk-insight has a custom minimal menu (Open / Copy path / Select in Explorer). The gap is significant for daily-use workflows.

This is a feasibility question: exposing a native Shell context menu from a Tauri/Rust application involves COM, unsafe code, and distribution risks. It may not be achievable in v0.4.0. See Section 7 (Explorer native context menu feasibility study).

### Condition 4 — App-wide UI polish: looks like a daily tool, not a dev prototype

**Why**: disk-insight currently has visible "made-in-dev" characteristics: inconsistent spacing, mixed typography, card layout that doesn't match a productivity tool aesthetic. A daily tool needs to feel finished.

See Section 6 (App-wide UI polish).

### Condition 5 — Arbitrary folder scan: not limited to drive roots

**Why**: WizTree can scan a specific folder without scanning the full drive. disk-insight currently requires a full drive MFT scan first. [TBD whether a folder-root mode is feasible while preserving speed]

See Section 8 (Arbitrary folder scan feasibility).

## 2. Current weaknesses vs WizTree

### Critical (blocks switchover)

| Weakness | Detail |
|----------|--------|
| No global file/folder search | WizTree allows typing to filter the entire tree. disk-insight has no cross-tree search. |
| TreeView expansion lost on rescan | After a rescan, TreeView collapses entirely. WizTree remembers expansion state. |
| No keyboard navigation | Mouse-only. WizTree is fully keyboard-operable. |
| No proportional size bar in TreeView | Numeric size only; no visual weight. Hard to spot large items at a glance. |
| D: warm is ~8–12s slower than WizTree | C: warm disk-insight is likely faster; D: warm it is slower. No clear overall speed advantage. |
| No drive capacity / free space display | WizTree shows used/free/total at a glance. disk-insight does not. |
| Explorer native context menu missing | WizTree exposes full Shell context menu. disk-insight has minimal custom menu. |
| "Dev prototype" UI appearance | Spacing, typography, and layout are inconsistent. Not a finished daily tool. |

### High (noticeable but not a blocker)

| Weakness | Detail |
|----------|--------|
| No virtual scroll for large folders | 200+ children show a warning. WizTree renders large lists smoothly. |
| Drive root only (no folder scan) | Cannot target a specific subfolder without full drive scan. |
| Path selection lost on rescan | Selected folder and direct children clear on every rescan. |
| No file type / category column | File extension or category not shown in tree. |

### Medium

| Weakness | Detail |
|----------|--------|
| Breadcrumb limited to one level | Multi-level path navigation requires repeated clicks. |
| Size accuracy divergence (WOF / hardlinks) | Bounded and documented, but visible to careful users. |

## 3. TreeView visibility and operability — improvement candidates

### 5.2 D: drive — performance analysis

D: CLI warm breakdown (K-5b run 2, post-N-2b):
- read_mft: 53,377 ms → **~90% of total scan time**
- Remaining phases: ~5,762 ms (~10%)

**read_mft is entirely dominant on D:.** This has a critical implication for optimization:

- `children_map` lazy build (K-5c): saves ~3.3s at scan time. On C: (~10s total), this is ~33% savings. On D: (~60s total), this is ~5% savings — barely noticeable.
- `wof_size_map` lazy build: ~0.3s savings. Negligible for D:.
- The only way to meaningfully improve D: warm speed is to reduce read_mft time — which requires parallel I/O (high risk, deferred beyond v0.4.0).

**K-5c (children_map lazy build) is primarily a C: optimization, not a D: optimization.**

For v0.4.0, D: performance is likely to remain ~60s CLI warm unless high-risk I/O changes are made.
The goal for D: should be: **"explain the gap and set an honest target, not necessarily close it."**

### 5.3 N-2b impact on D:

K-5b measured D: CLI warm at ~59–63s. README says ~54s. The discrepancy is likely due to N-2b (`wof_size_map` addition).

| Condition | D: CLI warm | Notes |
|-----------|------------|-------|
| Pre-N-2b (README) | ~54s | Source unclear; possibly from K-1 era |
| Post-N-2b (K-5b) | ~59–63s | K-5b release, run 1 possibly semi-cold |

If N-2b added ~5–9s to D: scans, that is significant and should be investigated.
However, K-5b run 1 may have been semi-cold (first D: scan after C: runs), which inflates the value.
A fresh D: warm measurement (two consecutive runs, no other scans before) would clarify this.

### 5.4 Cold cache targets — C: only

Cold cache targets apply to C: only. D: cold targets cannot be set until D: cold is measured.

| Stage | Target | Prerequisite | Notes |
|-------|--------|-------------|-------|
| Target A | C: cold Tauri UI ≤18s | K-5d warm measurement first | [inference] children_map lazy build may save ~3s cold: 23→20s |
| Stretch Target | C: cold Tauri UI ≤15s | Target A + additional optimization | Requires ~8s total reduction; children_map alone likely insufficient |

**23s → 15s requires ~8s reduction.** children_map saves ~3.3s. The remaining ~5s gap cannot be closed without:
- cold read_mft measurement (K-1d, never done) to understand the I/O contribution
- additional lazy-build or IPC-size optimizations
- or parallel I/O (high risk, deferred)

**Stretch Target (≤15s) remains conditional — feasibility to be judged after K-5c result.**

## 8 (old §7). Explorer native context menu — feasibility study

**Condition 3**: WizTree exposes the full Windows Shell context menu on right-click.

### What WizTree provides

Right-clicking a path opens the standard Windows Explorer context menu:
Open, Open with, Copy, Delete, Properties, Send To, shell extension items, etc.

### Feasibility questions [TBD]

| Question | Notes |
|----------|-------|
| Can Tauri invoke a Windows Shell context menu at arbitrary screen position? | Requires Win32 `IContextMenu` COM interface via Rust [TBD] |
| What unsafe / COM code is required? | `IShellFolder`, `IContextMenu`, `QueryContextMenu`, `InvokeCommand` — complex [TBD] |
| Does this require administrator privileges? | Likely not for display; some items may require elevation [TBD] |
| Distribution risk? | COM dispatch may vary across Windows versions / shell extensions [TBD] |
| Stability risk? | Third-party shell extensions can crash the host process [TBD] |

### Risk assessment (preliminary) [inference]

Technically possible but carries:
- High implementation complexity (COM, unsafe, lifetime management)
- Potential instability from third-party shell extensions
- Maintenance burden across Windows versions

**v0.4.0 recommendation**: Feasibility study only. If COM path looks manageable, plan for v0.5.0. If risk is too high, strengthen the custom context menu instead.

### Alternative: strengthen custom context menu

If native Shell menu is deferred, expand the custom menu:
- Open in Explorer (folder)
- Select in Explorer (file)
- Copy path / Copy name
- Open terminal here (`wt.exe` or `cmd.exe`)
- Properties (`ShellExecuteW` with "properties" verb)

Lower risk; can be done in v0.4.0 without COM [inference].

## 9 (old §8). Arbitrary folder scan — feasibility study

**Condition 5**: WizTree can scan a specific folder without scanning the full drive.

### Current behavior [measured — code inspection]

disk-insight requires a full drive scan (MFT traversal of the entire volume).

### Feasibility options [TBD]

| Option | Speed | Complexity | Notes |
|--------|-------|-----------|-------|
| MFT full scan + filter to target path (display-layer re-root) | Fast (MFT still read once) | Low | Uses cached data; no new scan |
| Filesystem walk for target path (non-MFT) | Slower on large drives | Low | Does not require admin for most paths |
| MFT scan with early cutoff at target path | Complex | High | MFT is not path-ordered [measured — architecture] |

**Likely best approach**: MFT full scan (existing) + path filter applied at display layer.
User selects a folder as "root" after the full scan; TreeView and children re-rooted at that path.
No new scan needed; uses cached `children_map` data. [inference — needs code investigation]

**Implementation boundary**: Feasibility study for v0.4.0. Implementation only if architecture supports it without new MFT reads or new Tauri commands.
