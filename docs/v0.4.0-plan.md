# v0.4.0 Plan — WizTree alternative candidate

**Date (initial)**: 2026-05-27  
**Date (revised)**: 2026-05-27  
**Status**: Planning only — no code changes in this document  
**Goal**: Define the conditions under which a user would choose disk-insight over WizTree  

> **Note on notation**  
> - `[observed]` — confirmed by measurement or code inspection  
> - `[inference]` — reasonable extrapolation, not yet measured  
> - `[TBD]` — requires investigation before deciding  

disk-insight v0.3.0 is a **safe-viewer** milestone: delete-free, reclaimable estimate, direct children navigation.
v0.4.0 targets **WizTree alternative candidate** — not a replacement, but a state where a user who knows WizTree
can consciously choose disk-insight for daily inspection work. The v0.3.0 safe-viewer positioning is preserved
and extended, not replaced.

---

## 1. Conditions for WizTree switchover

The following are the user-facing conditions that must hold for v0.4.0 to reach "alternative candidate" level.
Each condition maps to one or more implementation items in later sections.

### Condition 1 — Speed: disk-insight is faster, or not noticeably slower

**Why**: WizTree's core selling point is speed. If disk-insight is slower, there is no reason to switch.

| Scenario | v0.3.0 (observed) | WizTree (observed) | Gap | Target |
|----------|-------------------|--------------------|-----|--------|
| C: warm cache (SSD) | ~10–11s | ~15s | **disk-insight wins** [observed] | Maintain |
| C: cold cache (post-reboot) | ~23s | ~15s | ~8s slower [observed] | ≤18s (Target A) / ≤15s (Stretch) |
| D: warm cache (HDD) | ~54s | ~51s | ~3s slower [observed] | Acceptable for HDD |

Cold cache is the main gap. The 23s → 15s improvement requires ~8s reduction.
`children_map` lazy build is estimated at ~3.3s saving [inference from profiling].
Closing to ≤15s cold cache likely requires additional optimization beyond `children_map` alone.
See Section 4 for details and the two-stage target.

### Condition 2 — TreeView UI: easy to identify deletion candidates

**Why**: WizTree's tree shows Name / Size / Type with proportional size bars, making large items visually obvious. disk-insight currently shows numeric sizes without visual weight. `「削除候補の当たり」を付けにくい`

Key gaps:
- No proportional size bar in tree rows [observed]
- No file type / category column [observed]
- Folder vs file distinction is subtle [observed]
- All rows look similar regardless of size [observed]

See Section 5 (Explorer-like TreeView UI).

### Condition 3 — Right-click context menu: equivalent to Explorer

**Why**: WizTree exposes the Windows Explorer shell context menu on right-click (Open, Delete, Properties, Send To, etc.). disk-insight has a custom minimal context menu (Open / Copy path). The gap is significant for daily-use workflows.

This is a feasibility question: exposing a native Shell context menu from a Tauri/Rust application involves COM, unsafe code, and distribution risks. It may not be achievable in v0.4.0. See Section 7 (Explorer native context menu feasibility study).

### Condition 4 — App-wide UI polish: looks like a daily tool, not a dev prototype

**Why**: disk-insight currently has visible "made-in-dev" characteristics: inconsistent spacing, mixed typography, card layout that doesn't match a productivity tool aesthetic. A daily tool needs to feel finished.

See Section 6 (App-wide UI polish).

### Condition 5 — Arbitrary folder scan: not limited to drive roots

**Why**: WizTree can scan a specific folder (e.g., `C:\Users\name\Documents`) without scanning the full drive. This is useful for quick targeted inspection. disk-insight currently requires a full drive MFT scan first. [TBD whether a folder-root mode is feasible while preserving speed]

See Section 8 (Arbitrary folder scan feasibility).

## 2. Current weaknesses vs WizTree

### Critical (blocks switchover)

| Weakness | Detail |
|----------|--------|
| No global file/folder search | WizTree allows typing to filter the entire tree. disk-insight has no cross-tree search. |
| TreeView expansion lost on rescan | After a rescan, TreeView collapses entirely. WizTree remembers expansion state. |
| No keyboard navigation | Mouse-only. WizTree is fully keyboard-operable. |
| No proportional size bar in TreeView | Numeric size only; no visual weight. Hard to spot large items at a glance. |
| Cold cache scan ~8s slower than WizTree | First scan after reboot is noticeably slower. |
| No drive capacity / free space display | WizTree shows used/free/total at a glance. disk-insight does not. |
| Explorer native context menu missing | WizTree exposes full Shell context menu. disk-insight has minimal custom menu. |
| "Dev prototype" UI appearance | Spacing, typography, and layout are inconsistent. Not a finished daily tool. |

### High (noticeable but not a blocker)

| Weakness | Detail |
|----------|--------|
| No virtual scroll for large folders | 200+ children show a warning. WizTree renders large lists smoothly. |
| Drive root only (no folder scan) | Cannot target a specific subfolder without full drive scan. |
| Path selection lost on rescan | Selected folder and direct children clear on every rescan. |
| No file type / category column | File extension or category not shown in tree. |

### Medium

| Weakness | Detail |
|----------|--------|
| Breadcrumb limited to one level | Multi-level path navigation requires repeated clicks. |
| Size accuracy divergence (WOF / hardlinks) | Bounded and documented, but visible to careful users. |

## 3. TreeView visibility and operability — improvement candidates

### Q2-A: Keyboard navigation (HIGH)

- Arrow Up/Down to move selection within visible rows
- Arrow Right to expand, Arrow Left to collapse
- Enter to confirm selection / open in direct children panel
- Home/End to jump to top/bottom of visible rows

`visibleRows` flat list is already in place [observed] — keyboard nav indexes directly into it. Architecturally ready; implementation is primarily event handling.

### Q2-B: Expansion state persistence across rescans (HIGH)

Store expanded paths as a `Set<string>` keyed by path string. After scan completes, re-expand matching paths.

Caveat: FRN-based IDs change across scans [observed]; path string is the stable key.

### Q2-C: Selection highlight (LOW — acceptable in v0.3.0)

Selected row uses `background: #0e639c`. Not a blocker.

### Q2-D: Expand-to-path (MEDIUM)

Auto-expand TreeView to show and select a node given its path string. Useful when drill-down in direct children panel should be reflected in the tree. Shares implementation with Q2-B.

### Q2-E: Size bar in TreeView rows (MEDIUM → see Section 5)

Proportional bar in the size cell, relative to root. See Section 5 for the full Explorer-like TreeView treatment.

## 4. Performance — cold cache measurement and optimization

### Current findings (K-5b) [observed]

| Scenario | disk-insight | WizTree |
|----------|-------------|---------|
| C: warm cache (SSD) | ~10–11s | ~15s |
| C: cold cache (post-reboot) | ~23s | ~15s |
| D: warm cache (HDD) | ~54s | ~51s |

**Warm cache: disk-insight already wins.** Cold cache is the only remaining speed gap.

### Cold cache target — two stages

| Stage | Target | Notes |
|-------|--------|-------|
| Target A | cold C: **≤18s** | Achievable with `children_map` lazy build alone [inference] |
| Stretch Target | cold C: **≤15s** | Matches WizTree. Requires additional optimization beyond `children_map`. |

The gap from 23s to 15s is ~8s. `children_map` lazy build is estimated at ~3.3s saving [inference].
Reaching ≤15s cold likely requires further changes (e.g., `wof_size_map` lazy build + additional phase savings).
**K-5c will be measured first; Stretch Target feasibility will be judged from that result.**

### Step R-2: Cold cache phase breakdown measurement (BEFORE optimization)

Before implementing K-5c, add phase-level timing to understand where the 23s is spent.
Target breakdown:

| Phase | Expected cost | Status |
|-------|--------------|--------|
| MFT read (I/O) | Dominant [inference] | [TBD: measure] |
| Node build / tree assembly | Medium [inference] | [TBD: measure] |
| `children_map` build | ~3.3s [inference] | [TBD: measure] |
| `wof_size_map` build | ~0.3s [inference] | [TBD: measure] |
| Serialization / Tauri handoff | Small [inference] | [TBD: measure] |
| First render (React) | Small [inference] | [TBD: measure] |

If MFT I/O dominates (>15s of the 23s), the only path to ≤15s cold is parallel I/O (high risk).
If non-I/O phases dominate, lazy build strategies may be sufficient.

### Optimization candidates (ranked)

| Candidate | Expected saving | Risk | Status |
|-----------|----------------|------|--------|
| `children_map` lazy build (K-5c) | ~3.3s [inference] | Low | Not implemented |
| `wof_size_map` lazy build (K-5d) | ~0.3s [inference] | Low | Not implemented |
| Parallel MFT I/O | High potential | **High** | Deferred beyond v0.4.0 |

### Measurement plan

1. **R-2**: Add phase-level timing. Measure cold C: breakdown. Record each phase.
2. **R-3 (K-5c)**: Implement `children_map` lazy build. Measure cold C: before/after.
3. If result ≤18s → Target A passed. Evaluate Stretch Target feasibility.
4. If result >18s → re-examine phase breakdown; consider whether Stretch Target is realistic for v0.4.0.
5. **K-5d**: Implement `wof_size_map` lazy build after K-5c if gap remains.
6. **D: HDD (54s vs 51s)**: Acceptable. No optimization target for v0.4.0.

## 5. Explorer-like TreeView UI

This is a new section addressing Condition 2 (easy to identify deletion candidates).
The goal is to make the TreeView work like WizTree's tree: users should be able to
identify large items, understand file types, and form "deletion candidate" hypotheses at a glance.

### Q5-A: Proportional size bar in tree rows (HIGH)

A thin colored bar inside the size cell, proportional to the node's share of the root's total size.
This is WizTree's primary visual cue.

- Implementation: CSS background gradient or a `<span>` overlay on the size cell
- Logic: `node.size / root.size * 100%` as bar width
- No Rust/Tauri change needed — purely React/CSS [inference]
- **This is the single highest-visual-impact change** for WizTree comparison

### Q5-B: File type / category column (MEDIUM)

Show file extension or category (Image, Video, Archive, Code, etc.) in a column.
Currently only name and size are shown.

- Type derived from path extension — no new Tauri command needed [inference]
- Category grouping adds filtering capability (future)

### Q5-C: Folder vs file visual distinction (MEDIUM)

Folder rows and file rows look similar in the current TreeView.
Add an icon or color distinction to make folders immediately obvious.
WizTree uses icons; disk-insight can use a minimal folder indicator.

### Q5-D: Column header resize / reorder (LOW)

Name / Size / Type columns should be resizable. Low priority but affects "finished tool" feel.

### Q5-E: Percentage column (LOW)

Show each node's percentage of its parent's total. Complements the size bar.

## 6. App-wide UI polish

**Condition 4**: disk-insight must look like a finished daily tool, not a dev prototype.

### Observed issues [observed]

- Toolbar: button sizes, spacing, and visual weight are inconsistent
- Cards (summary card, reclaimable estimate card): border radius, shadow, padding vary
- Typography: heading sizes and font weights are not unified
- Direct children panel: header row height and padding differ from TreeView
- Color usage: blues and grays are mixed across components without a consistent palette

### Target state

- Consistent spacing system (4px / 8px / 16px grid)
- Unified card style (same border, shadow, radius across all cards)
- Toolbar feels like a productivity tool (VS Code-like density, not a form)

- Color palette defined and used consistently

### Implementation approach

Polish should be done as a dedicated pass (R-6 or nearby), not scattered across feature PRs.
A "visual before/after" check against WizTree screenshots will guide the review.
No logic changes — CSS / layout only.

## 7. Explorer native context menu — feasibility study

**Condition 3**: WizTree exposes the full Windows Shell context menu on right-click.
disk-insight has a custom minimal menu (Open / Copy path / Select in Explorer).

### What WizTree provides

Right-clicking a path in WizTree opens the standard Windows Explorer context menu:
Open, Open with, Copy, Delete, Properties, Send To, shell extension items, etc.

### Feasibility questions [TBD]

| Question | Notes |
|----------|-------|
| Can Tauri invoke a Windows Shell context menu at an arbitrary screen position? | Requires Win32 `IContextMenu` COM interface via Rust [TBD] |
| What unsafe / COM code is required? | `IShellFolder`, `IContextMenu`, `QueryContextMenu`, `InvokeCommand` — complex [TBD] |
| Does this require administrator privileges? | Likely not for display, but some items may require elevation [TBD] |
| Distribution risk? | COM dispatch may behave differently across Windows versions / shell extensions [TBD] |
| Stability risk? | Third-party shell extensions can crash the host process [TBD] |

### Risk assessment (preliminary) [inference]

Exposing a native Shell context menu from a Tauri/Rust process is technically possible but carries:
- High implementation complexity (COM, unsafe, lifetime management)
- Potential instability from third-party shell extensions
- Maintenance burden across Windows versions

**v0.4.0 recommendation**: Treat as **feasibility study only**.
If the COM path looks manageable after investigation, plan for v0.5.0.
If the risk is too high, strengthen the custom context menu instead.

### Alternative: strengthen custom context menu

If native Shell menu is deferred, expand the custom context menu to cover more cases:
- Open in Explorer (folder)
- Select in Explorer (file)
- Copy path
- Copy name only
- Open terminal here (`wt.exe` or `cmd.exe`)
- Properties (launch `ShellExecuteW` with "properties" verb)

This is lower risk and can be done in v0.4.0 without COM [inference].

## 8. Arbitrary folder scan — feasibility study

**Condition 5**: WizTree can scan a specific folder without scanning the full drive.

### Current behavior [observed]

disk-insight requires a full drive scan (MFT traversal of the entire volume).
The user selects a drive letter; there is no folder-level scan target.

### Feasibility options [TBD]

| Option | Speed | Complexity | Notes |
|--------|-------|-----------|-------|
| MFT full scan + filter to target path | Fast (MFT still read once) | Low | Post-scan filter; full drive data in memory |
| MFT scan with early cutoff at target path | Complex | High | MFT is not sequentially ordered by path [observed] |
| Filesystem walk (non-MFT) for target path | Slower than MFT on large drives | Low | Does not require admin for most paths |

**Likely best approach**: MFT full scan (existing) + path filter applied at display layer.
User selects a folder as "root" after the full scan, TreeView and children re-rooted at that path.
No new scan needed; uses cached data. [inference — needs code investigation]

### UI considerations [TBD]

- Option A: Folder picker dialog (Windows `IFileDialog`)
- Option B: Path text input in toolbar
- Option B is simpler; Option A is more discoverable

### Implementation boundary

This is a **feasibility study** for v0.4.0. Implementation timeline depends on:
1. Whether path-filter-as-root works with existing `children_map` architecture
2. Whether a new `scan_folder` Tauri command is needed or can be avoided

**Constraint**: No new MFT re-read or additional Rust core scan commands in v0.4.0 unless the architecture forces it.

## 9. Virtual scroll — conditions for implementation

Virtual scroll is NOT needed for v0.4.0 unless triggered by daily-use testing.

**Trigger condition**: A folder commonly encountered in daily inspection has >200 direct children
AND the warning/truncation makes disk-insight visibly inferior to WizTree.

Candidate paths:
- `C:\Windows\System32` (~4,000+ files) — less likely to be inspected via direct children
- `C:\Users\<user>\AppData\Local` — possible in daily use

`visibleRows` flat list is virtual-scroll-ready [observed]. `@tanstack/react-virtual` can be added without architectural change.

**v0.4.0 decision**: Implement if testing triggers the condition. Otherwise defer to v0.5.0+.

## 10. Differentiation factors vs WizTree

These advantages must be preserved as v0.4.0 evolves:

| Factor | disk-insight | WizTree |
|--------|-------------|---------|
| **Delete-free safety** | No delete action (by design) | Delete action present — accidental deletion risk |
| **Reclaimable estimate with confidence** | High/Medium/Low confidence, caution text, `not_recommended` flag | No equivalent |
| **WOF comparison mode** | `wof_adjusted` policy shows compressed backing size | Not exposed |
| **System path warnings** | "Not recommended as deletion target" on system paths | No equivalent |
| **Open source / auditable** | Source available; no hidden behavior | Closed source |
| **License-free** | Rust + MIT/Apache; usable in work environments | WizTree requires commercial license |

## 13. v0.4.0 completion conditions

v0.4.0 is complete when a user who knows WizTree can consciously choose disk-insight for daily inspection work without feeling a critical gap.

### Required (all must pass)

- [ ] **Cold cache C: ≤18s** (Target A): K-5c measured and passing
- [ ] **Keyboard navigation**: Up/Down selects rows; Right/Left expands/collapses; Enter opens direct children
- [ ] **TreeView expansion persistence**: Previously expanded folders restored after rescan
- [ ] **Proportional size bar in TreeView**: Large items visually obvious at a glance
- [ ] **Global search**: Top-dirs filter by name/path (minimum viable search)
- [ ] **Drive capacity display**: Used / free / total visible in UI
- [ ] **App-wide UI polish**: Spacing, typography, cards unified; looks like a finished daily tool

### Conditional (if triggered by testing)

- [ ] **Cold cache C: ≤15s** (Stretch Target): Only if K-5c + K-5d show it is achievable
- [ ] **Virtual scroll**: Only if 200-child cap creates a visible daily-use blocker
- [ ] **Custom context menu expanded** (open terminal, properties): Only if native Shell menu is deferred

### Feasibility studies (docs/research, not implementation)

- [ ] **Arbitrary folder scan**: Architecture investigation complete; recommendation written
- [ ] **Explorer native context menu**: COM/unsafe risk assessed; v0.4.0 / v0.5.0 decision made

### Not required for v0.4.0

- Cold cache ≤15s (Stretch Target — conditional)
- Hardlink dedup / WinSxS correction
- Treemap visualization
- Explorer native context menu implementation
- Arbitrary folder scan implementation
- Delete / move / rename action (never)
- Byte-exact WizTree size matching

### Tag name

`v0.4.0-wiztree-candidate` — marks the milestone as a candidate, not a replacement.
Final judgment is made by the user after hands-on testing against WizTree.

## Summary

v0.4.0 reframes the goal from "operability improvement" to "state where WizTree switchover is convincing."

Five user-facing conditions define readiness:
1. Speed — warm already wins; cold cache must close to ≤18s (Target A)
2. TreeView UI — proportional size bars and type distinction make large items obvious at a glance
3. Right-click context menu — feasibility study; custom menu strengthened if native Shell is deferred
4. UI polish — finished-tool appearance, not a dev prototype
5. Arbitrary folder scan — feasibility study; implementation only if architecture supports it cleanly

disk-insight's delete-free safety and reclaimable estimate remain core differentiators —
preserved and not replaced as v0.4.0 evolves toward WizTree navigation parity.
