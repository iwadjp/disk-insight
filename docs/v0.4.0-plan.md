# v0.4.0 Plan — WizTree alternative candidate

**Date**: 2026-05-27  
**Status**: Planning only — no code changes in this document  
**Goal**: Define what v0.4.0 needs to achieve to reach "WizTree alternative candidate" level  

disk-insight v0.3.0 is a **safe-viewer** milestone — delete-free, reclaimable estimate, direct children navigation. It is not yet at WizTree replacement level. v0.4.0 targets "alternative candidate": a user who would normally reach for WizTree should be able to use disk-insight instead for most daily-use tasks.

---

## 1. Current weaknesses vs WizTree

### Critical (blocks daily use)

| Weakness | Detail |
|----------|--------|
| No global file/folder search | WizTree allows typing to filter the entire tree. disk-insight has no cross-tree search. The user must know which subtree to navigate. |
| TreeView expansion lost on rescan | After a rescan, the TreeView collapses entirely. WizTree remembers expansion state. This makes iterative inspection painful. |
| No keyboard navigation | Arrow keys, Enter to expand/collapse, Tab between panels. WizTree is keyboard-operable. disk-insight is mouse-only. |

### High (noticeable gap)

| Weakness | Detail |
|----------|--------|
| No virtual scroll in large folders | Folders with 200+ children show a warning. WizTree renders large lists smoothly. |
| No size bar / treemap visualization | WizTree shows proportional size bars in the tree. disk-insight shows only numeric size. |
| No drive capacity / free space display | WizTree shows drive usage context at the top. disk-insight shows no total/free/used breakdown. |
| Cold cache scan latency | First scan after reboot: C: ~20s, D: ~70s. WizTree: C: ~15s. Cold scan is visibly slower on first-run experience. Progress strip partially mitigates perception but not actual wait time. |

### Medium (rough edges)

| Weakness | Detail |
|----------|--------|
| Right pane resets on scan | Direct children panel clears on every rescan. |
| Path selection not preserved | Selecting a folder, then rescanning, loses context. |
| Size accuracy divergence | WOF areas and hard links diverge from WizTree/Explorer. Bounded and documented, but visible to attentive users. |

## 2. TreeView visibility and operability improvement candidates

### Q2-A: Keyboard navigation (HIGH priority)

- Arrow Up/Down to move selection within visible rows
- Arrow Right to expand, Arrow Left to collapse
- Enter to confirm selection / open in direct children panel
- Home/End to jump to top/bottom of visible rows

Implementation note: `visibleRows` flat list is already in place — keyboard nav indexes directly into it. This is architecturally ready.

### Q2-B: Expansion state persistence across rescans (HIGH priority)

On rescan, restore expansion state for paths that still exist in the new scan tree. Store expanded paths as a `Set<string>` keyed by path string. After scan completes, re-expand matching paths in the new tree.

Caveat: FRN-based IDs change across scans; path string matching is the safe key.

### Q2-C: Selection highlight visibility (LOW — already improved in v0.3.0)

Selected row uses `background: #0e639c`. Acceptable. Not a blocker.

### Q2-D: Expand-to-path (MEDIUM)

Given a path string (e.g., from direct children drill-down), auto-expand the TreeView to show and select that node. Useful when drilling into a subfolder and wanting the tree to follow. Complex to implement — defer unless navigation feels disconnected.

### Q2-E: Size bar in TreeView rows (MEDIUM)

A thin proportional bar inside each row's size cell, relative to the root node. Gives WizTree-like visual weight. Purely cosmetic, no logic change needed. Can be done with a CSS background gradient on the size cell.

## 3. Direct children panel — next improvement candidates

### Q3-A: Preserve selected path and filter across rescans (MEDIUM)

After a rescan, if the previously selected path still exists in the new tree, re-select it and reload direct children. Currently the panel clears entirely. Small UX win for iterative workflows.

### Q3-B: Column sort persistence (LOW — already in v0.3.0 via session prefs)

Sort direction is saved. No further action needed.

### Q3-C: Multi-level breadcrumb with clickable segments (LOW)

Currently breadcrumb shows one level up. Full path breadcrumb with clickable segments (like Explorer address bar) would allow faster navigation. Medium effort.

### Q3-D: File count column (LOW)

Show number of children alongside size. Useful for identifying directories with many small files vs. few large ones.

### Q3-E: Direct link to parent TreeView node (MEDIUM)

Clicking a path in direct children selects it; the TreeView should expand and scroll to match. See Q2-D (expand-to-path). Both can share the same implementation.

## 4. Cold cache / performance — continuation measurement plan

### Current findings (K-5b)

| Scenario | disk-insight | WizTree |
|----------|-------------|---------|
| C: warm cache (SSD) | ~10–11s | ~15s |
| C: cold cache (post-reboot) | ~23s | ~15s |
| D: warm cache (HDD) | ~54s | ~51s |

**Warm is already ahead of WizTree. Cold is the remaining gap.**

### K-5 optimization candidates (ranked by expected impact)

| Candidate | Expected saving | Risk | Status |
|-----------|----------------|------|--------|
| `children_map` lazy build | ~3.3s | Low | Not implemented |
| `wof_size_map` lazy build | ~0.3s | Low | Not implemented |
| Parallel MFT I/O | High potential, high risk | High | Deferred |

### Measurement plan for v0.4.0

1. **K-5c**: Implement `children_map` lazy build (populate on first `get_children` call, not at scan end). Measure cold-cache C: scan time before and after.
2. **K-5d**: Implement `wof_size_map` lazy build if K-5c alone closes the gap to ≤15s cold.
3. **Target**: cold-cache C: ≤15s (match WizTree). If not achieved, document gap and defer parallel I/O to v0.5.0+.
4. **Warm**: No action needed — already ahead.
5. **D: HDD**: 54s vs 51s — acceptable for HDD. No optimization target for v0.4.0.

## 5. Virtual scroll — conditions for implementation

Virtual scroll is NOT needed for v0.4.0 unless the following condition is met:

**Trigger condition**: A folder commonly encountered in daily use has >200 direct children AND the warning/truncation makes the tool visibly inferior to WizTree.

Current behavior: folders with >200 children show a warning and are capped. WizTree renders them without restriction.

### Candidate paths that may trigger this

- `C:\Windows\System32` (~4,000+ files) — less likely to be inspected in direct children
- `C:\Users\<user>\AppData\Local` — possible
- Project root folders with many files — possible

### Implementation readiness

`visibleRows` flat list in `ui/src/main.tsx` is already virtual-scroll-ready (indexed, non-recursive render). `@tanstack/react-virtual` can be added without architectural change.

**v0.4.0 decision**: Implement virtual scroll if testing shows the 200-child cap creates a visible daily-use blocker. Otherwise defer to v0.5.0+.

## 6. Explorer integration — priority

### Current state (v0.3.0)

- Open folder in Explorer (`open_in_explorer`)
- Select file in Explorer (`select_in_explorer`)
- Copy path to clipboard
- Right-click context menu on direct children rows

This is **sufficient for v0.4.0**. No new Explorer integration planned.

### Lower priority for v0.4.0

- Open containing folder for items in top-dirs/top-files lists (currently available in direct children only) — useful but not critical
- Drag-and-drop from disk-insight to Explorer — not planned

### Not planned

- Shell extension / Explorer column handler — out of scope
- Windows context menu registration — out of scope

## 7. Differentiation factors vs WizTree

disk-insight has unique advantages that WizTree does not provide:

| Factor | disk-insight | WizTree |
|--------|-------------|---------|
| **Delete-free safety** | No delete action exists | Delete action present (risk of accidents) |
| **Reclaimable estimate with confidence** | Confidence (High/Medium/Low), basis, caution, `not_recommended` flag | No equivalent |
| **WOF comparison mode** | `wof_adjusted` policy shows compressed backing size | Not exposed |
| **System path warnings** | `Not recommended as deletion target` on system paths | No equivalent |
| **Open source / auditable** | Can be verified — no hidden delete behavior | Closed source |
| **License-free** | Rust + MIT/Apache — no license restriction for work environments | WizTree requires a license for commercial use |

These differentiators should be preserved and highlighted as v0.4.0 evolves toward WizTree parity on navigation.

## 8. v0.4.0 — should-do / should-not-do

### Should do

| Item | Why |
|------|-----|
| Keyboard navigation in TreeView (Q2-A) | Critical daily-use gap; architecturally ready |
| TreeView expansion persistence across rescans (Q2-B) | High-friction regression on every rescan |
| `children_map` lazy build — K-5c (cold cache optimization) | Closes the cold-cache speed gap vs WizTree |
| Drive capacity / free space display | Prominent WizTree feature; affects first impression |
| Global folder/file search (name filter across tree) | Critical navigation gap; most-requested WizTree feature |
| Virtual scroll (conditional — if 200-child cap is a blocker) | Only if triggered by daily-use testing |

### Should not do

| Item | Reason |
|------|--------|
| Delete action | Intentionally excluded; safety is a differentiator |
| Hardlink dedup / WinSxS correction | Size accuracy is bounded and documented; accuracy work is high effort / low return at v0.4.0 |
| WOF-adjusted as default | Experimental; don't change default behavior |
| New Tauri commands beyond existing 7 | No new MFT reads; no new filesystem writes |
| MFT re-read / re-scan logic changes | Core scan logic is stable; don't touch |
| Parallel MFT I/O | High risk, deferred beyond v0.4.0 |
| Treemap visualization | Useful but not a WizTree parity requirement; deferred |

## 9. v0.4.0 completion conditions

v0.4.0 is complete when a user who would normally reach for WizTree can use disk-insight for most daily-use tasks without feeling a critical gap.

### Required (all must pass)

- [ ] **Keyboard navigation**: Up/Down selects rows in TreeView; Right/Left expands/collapses; Enter opens in direct children panel
- [ ] **TreeView expansion persistence**: After rescan, previously expanded folders are restored (path-string match)
- [ ] **Global search**: Typing in a search box filters the top-dirs list by path segment (minimum: top-dirs filter; bonus: full tree search)
- [ ] **Drive capacity display**: Used / free / total shown somewhere in the UI (header or toolbar)
- [ ] **Cold cache C: ≤15s**: Warm is already passing; cold must close to WizTree level

### Conditional (if triggered by testing)

- [ ] **Virtual scroll**: If the 200-child cap creates a visible daily-use blocker in practice
- [ ] **Breadcrumb clickable segments**: If multi-level navigation is frustrating in practice

### Not required for v0.4.0

- Hardlink dedup / WinSxS correction
- Treemap visualization
- Delete action (never)
- Byte-exact WizTree size matching

### Tag name

`v0.4.0-wiztree-candidate` — marks the milestone as a candidate, not a replacement. The user decides after testing.

---

## Summary

v0.4.0 adds the navigation layer that v0.3.0 intentionally deferred:
keyboard control, persistent expansion, global search, and drive capacity context.
Combined with disk-insight's existing safety differentiators (delete-free, reclaimable estimate),
these additions should bring it to "alternative candidate" level for daily inspection work.

The safe-viewer positioning of v0.3.0 is preserved and extended — not replaced.
