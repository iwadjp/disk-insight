disk-insight v0.3.0 is a **safe-viewer** milestone: delete-free, reclaimable estimate, direct children navigation.
v0.4.0 targets **WizTree alternative candidate** — not a replacement, but a state where a user who knows WizTree
can consciously choose disk-insight for daily inspection work. The v0.3.0 safe-viewer positioning is preserved
and extended, not replaced.

---

## 1. Conditions for WizTree switchover

### Condition 1 — Speed: disk-insight is not noticeably slower, or is faster

**Why**: WizTree's core selling point is speed. If disk-insight is meaningfully slower, there is no reason to switch.

#### K-5f-1 read_mft low-risk I/O experiment (2026-05-27) [measured]

K-5f-1 tested two low-risk changes in `src/mft_probe.rs`:

- add `FILE_FLAG_SEQUENTIAL_SCAN` to the volume handle opened by `get_mft_info`
- replace the model-path extent-sized `ReadFile` with 4 MB chunked reads,
  preserving extent order and destination buffer offsets

Additional read timing now reports:

- buffer allocation / zero-init time
- extent runlist decode time
- read loop time
- throughput in MB/s
- chunk size

Result: the experiment did **not** improve D: in the local CLI perf-model
measurement. It likely made D: worse.

| Drive / Run | Total | read_mft | read_mft detail | Notes |
|-------------|------:|---------:|-----------------|-------|
| C: K-5f-1 sample | 7,529 ms | 5,442 ms | 356.2 MB/s, 4 MB chunks | Similar overall to K-5c C: 7,233 ms |
| D: K-5f-1 run1 | 54,029 ms | 49,031 ms | 113.5 MB/s, 4 MB chunks | Comparable to K-5c run2 read_mft |
| D: K-5f-1 run2 | 60,392 ms | 57,789 ms | 96.3 MB/s, 4 MB chunks | Worse |
| D: K-5f-1 run3 | 56,743 ms | 54,250 ms | 102.6 MB/s, 4 MB chunks | Worse |
| D: K-5f-1 adopted run2/run3 | **58,568 ms** | **56,020 ms** | n/a | Worse than K-5c adopted 52,989 ms |

K-5f-1 judgment:

- 4 MB chunked reads plus `FILE_FLAG_SEQUENTIAL_SCAN` did not provide the hoped
  D: improvement in this measurement.
- D: remains dominated by `read_mft`.
- The next major speed improvement would likely require riskier MFT I/O work
  such as physical-order reads, overlapped I/O, parallel I/O, or caching.
- Those changes are high risk and should not be pursued for v0.4.0 unless speed
  becomes a renewed blocker.
- Cold cache remains unmeasured.

- **Adopted**: K-5c (ArenaCache lazy build), K-5f-2a (FILE_FLAG_SEQUENTIAL_SCAN only).
- **Rejected**: Chunked reads (4MB/32MB), LCN-ordered reads, mft_raw path, zero-init optimization, no-extra-compute. These either worsened performance or provided negligible gains compared to their implementation risks.
- **Diagnostics**: Parse spikes were investigated but proved transient; no code changes required.

Final Benchmark Results (Release Tauri UI):
- **Warm C: (~1.3M files)**: disk-insight UI ~7.4s vs WizTree ~12.3s → **disk-insight is ~4.9s faster**.
- **Warm D: (~4.5M files, HDD)**: disk-insight UI ~52.6s vs WizTree ~55.4s → **disk-insight is ~2.8s faster**.
- **Cold-ish D: (HDD)**: disk-insight stopwatch ~50.5s vs WizTree ~49.1s → **WizTree is ~1.4s faster (stopwatch basis)**.

Final Speed Judgment:
- **Warm speed**: Goals achieved. disk-insight is competitive or superior on both SSD and HDD when warm.
- **Cold-ish speed**: Goal "comparable" achieved, but not "clearly superior". disk-insight is extremely stable (~46.7s read_mft), but WizTree remains slightly ahead.
- **Roadmap**: Further read_mft improvements (read-ahead, MFT cache, parallel/overlapped I/O) are high-risk and deferred beyond v0.4.0.
- **Positioning**: Maintain **“WizTree alternative candidate”**. Performance is sufficient to proceed to UI/UX improvements.

Next Phase:
- Transition to **Condition 2 (TreeView UI)** and **Condition 4 (UI Polish)**.
- Focus on: Size bars (Q5-A), Keyboard navigation (Q2-A), Expansion persistence (Q2-B).

- The only way to meaningfully improve D: further is MFT I/O work, which is

  a blocker.

**D: warm status**: K-5c after-measurement adopted warm is 52.989s vs WizTree

positioning, while avoiding "WizTree replacement completed" claims.
